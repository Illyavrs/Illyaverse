# Lazer replay ingestion and export

Native solo play uses the existing authenticated spectator hub: `BeginPlaySession(scoreToken, state)`, `SendFrameData(bundle)`, and `EndPlaySession(finalState)`. The V2 aliases are also supported. Native clients do not upload a replay through a new multipart API. Score JSON is submitted through `PUT /api/v2/beatmaps/{beatmap}/solo/scores/{token}`; `GET /api/v2/scores/{score}/download` returns a binary `.osr` file.

Capture records and ordered frame chunks are persisted in PostgreSQL. A token is bound to its authenticated owner, beatmap, ruleset and current connection. Reconnecting retains recorded chunks, marks continuity as interrupted, and rejects the replaced connection's writer. Exact bundle retries are deduplicated. Score-before-end, end-before-score and concurrent delivery all finalize under a capture row lock. Quit releases temporary chunks. At most four unfinished or awaiting-submission captures are retained per user; expired unused tokens are cleaned up on a subsequent begin.

Before replay publication, the final frame header must match the stored submission's score, accuracy, combo, modifiers, hit statistics, maximum statistics, optional pauses and unmodified score. The generated replay is written through a temporary file, synced and renamed before the database references it. SHA-256 and an audit record are saved, then temporary chunks are deleted. A validated passed native lazer score publishes automatically only when its bound capture is complete. Score admission records `scores.native_publish` once in the transaction; capture retries preserve the score's state and any explicit `scores.verify` administrator decision, including pending or rejected. Native capture attachment no longer resets a published/rejected score to pending. These structural checks do not claim deterministic gameplay replay verification.

Website owners can upload an exported extended `.osr` to the existing `POST /api/v1/scores/{id}/replay` endpoint. Its inner score ID, user ID, outer username, beatmap checksum, ruleset, score, combo, legacy modifier bits and extended statistics/settings must match the stored score and lazer submission. An exact retry is idempotent; a different replay cannot replace an existing one. Website/API upload remains a staged path and does not establish native capture continuity or automatically publish a passed score. Pending downloads are owner-only in the native API; the website additionally permits score moderators. Restricted players' native replay downloads are hidden. Stable replay paths retain their legacy container behavior.

`replay_complete` is `true` for an uninterrupted recorded stream, `false` after a recorded reconnect, and `null` for uploaded/older files whose stream continuity was not observed. Completeness is required for automatic passed lazer publication, but does not by itself grant publication or override administrator decisions. It does not claim deterministic gameplay re-simulation. Interrupted captures remain downloadable by authorized users and pending; unfinished captures remain staged until finalization.

Startup and periodic recovery revisit up to 32 ended captures whose token already references a score. This covers a crash after committing `score_id` but before replay publication, without requiring the client to retry. Row locks make repeated/overlapping recovery idempotent; failures move behind untouched captures to avoid starving another user's replay. At most two native encoders run concurrently.

## Binary format and bounds

The exported container uses the public legacy `.osr` header, LZMA-compressed legacy frame text, the legacy online ID, then a signed 32-bit length and another LZMA stream containing `LegacyReplaySoloScoreInfo` JSON. The exporter uses scoring version `30000019`; metadata includes the solo score ID, user, full API mods/settings, statistics, maximum statistics, rank, pauses and unmodified total. An unavailable human-readable client version is left empty; the token's build hash remains in its own record.

Files are capped at 16 MiB; decompressed frames at 32 MiB/one million frames; decompressed metadata at 1 MiB; LZMA dictionaries at 8 MiB and decoder memory at 64 MiB. Frame bundles are already limited by the hub to 512 frames/32 KiB; durable chunks are capped at 64 KiB. Malformed lengths, trailing data, invalid coordinates/buttons, excessive declared decompression output, unknown hit results and mismatched identities are rejected. Legacy header score/combo/count widths remain bounded by the native format.

## Evidence and limitations

The committed synthetic fixture was produced by the installed official `LegacyScoreEncoder` in `osu.Game 2026.1005.1-tachyon+6cbcae7fbb764839a66c1adf564c2e1679242072`, not described as an unmodified latest stock client. It includes custom DT speed `1.2`, two replay frames and no personal data. The actual DLL produced a 379-byte `.osr`; the Rust parser read and bound it, and the Rust exporter produced 364 bytes. The installed official binary reader, SharpCompress decoder and typed `LegacyReplaySoloScoreInfo` JSON deserializer accepted the Rust file, including custom speed settings. The original DLL harness remains ignored scratch; no upstream implementation was copied.

Protocol tests cover this native fixture, metadata binding, truncation, trailing data, decompression limits and invalid frames. The live gateway test uses actual HTTP/WebSocket transports and a fresh PostgreSQL schema, with a small test ingestion adapter that persists fixture scores rather than invoking Sanctuary's pp calculator. It covers current native V1 methods and V2 aliases, custom DT settings, both delivery orders and their race, token ownership/expiry, duplicate bundles, idempotent finalization, reconnect continuity, stale writers, quit cleanup and pending/restricted download privacy. A separate website router/PostgreSQL test covers upload ownership, wrong score IDs, idempotency, replacement rejection and private downloads.

```powershell
# ILLYA_TEST_DATABASE_URL must identify a disposable database.
cargo test -p resonance-protocol lazer_replay
cargo test -p resonance native_replay_http_websocket_persistence -- --ignored --nocapture
cargo test -p sanctuary extended_replay_upload_permissions_and_idempotency -- --ignored --nocapture
```

The gateway test also simulates a restart-ready capture after committing its score reference: recovery publishes once and a second pass does no work. Database/filesystem interruption can leave unreferenced files requiring operator cleanup; full files are retained on uncertain commit acknowledgements to protect any committed reference. These tests prove the documented binary/transport paths with synthetic data. Actual game-host login, replay playback/re-simulation and complete native multiplayer score submission remain release checks; cross-client stable/lazer replay conversion is not claimed.
