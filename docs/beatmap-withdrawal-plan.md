# Reversible beatmap withdrawal — implemented and integration-tested

Ranking status is independent of availability: pending, ranked, loved and unranked maps remain public while their sets are active. The current source implements durable availability at canonical native-set identity, including official sets whose members have not all been cached. The final source, PostgreSQL, withdrawal UI and release-image protocol gates passed; related website regression is verified through the initial passing coverage and the corrected catalogue fixture. Retained deployment is still pending. See the [verification record](../.impeccable/review/beatmap-withdrawal-verification.md) for actual results and the native-client boundary. The [availability contract](beatmap-availability.md) documents administration and exact saved-receipt semantics.

Withdrawal must suppress public and native search/lookup/download, new score admission, playlist selection and new rounds while retaining immutable packages, files, hashes, IDs, aliases, existing scores, review decisions, replays, tokens, frozen rounds and audit history. Existing result/replay/history access continues under its normal privacy rules. Active ranked totals and best-play collections exclude withdrawn sets; restoration restores the contribution of retained qualified results.

Saved score retries remain idempotent. New score publication rechecks withdrawal inside its transaction; a gateway preflight is insufficient. Incomplete tokens/receipts stay retained, with publication denied until a valid restoration. A normal import, exact package retry or cached official response must never restore withdrawn content implicitly.

Identity resolvers must distinguish retained-and-withdrawn from absent; treating withdrawal as a miss would permit official rediscovery. Check durable state before cache hits/upstream requests, after waits and responses, and before publication/response. Share a consistent resource-lock order with import and score admission, audit changes and enqueue native set update events atomically. Cache invalidation is supplemental to the durable authority.

Implementation crosses Sanctuary maps/official archive/official metadata caches/score admission/ranking; Resonance native identity and archive helpers/stable web/lazer discovery and solo submission/room playlist-round-score processing; public and administrative website surfaces; and a new migration. Existing migration files and immutable identities must stay unchanged. Staff retained-content queries need an explicit history mode separate from active public discovery.

Verification must cover every ranking status, both local and official namespaces, cached IDs/hashes/filename selectors and archive fallbacks, warm/in-flight metadata caches, exact saved versus unsaved retries, room tokens and receipts, retained replay/history, removal/restoration of rank contribution, and atomic native update events. Relevant fixtures include map mutation/package/search/native-map, official archive/metadata, score mutation and room-score suites. Partial public filtering alone cannot establish this capability.

The additive migration 0020 preserves schema 0019 data, uses absent state as active revision zero, and retains restored state rows. Shared admission and exclusive state/publication fences use canonical set IDs in namespace `0x494c4f53`; multi-set callers take distinct ascending IDs after their existing authority locks. The staff writer acquires its set fence before its state row and never locks affected map, score, token, room or player rows. Historical PP/ranks are calculated live, so active eligibility changes without rewriting scores; lifetime totals remain retained.

Database publication triggers recheck authoritative availability after any lock wait. Matching persisted ingestion keys remain idempotent before and after that wait; unknown keys and different user/map/mode/variant partitions do not bypass withdrawal. Trigger functions are volatile so their individual statements use fresh snapshots; the catalogue predicate is stable for a coherent read query. These choices follow [PostgreSQL function snapshot semantics](https://www.postgresql.org/docs/17/xfunc-volatility.html). The new beatmap guard is named after the existing identity binder in the [documented trigger execution order](https://www.postgresql.org/docs/17/sql-createtrigger.html), preserving immutable native identity before checking admission.

`npm run test:availability:db` creates one uniquely named and labelled tmpfs PostgreSQL container. It applies 0001–0019, seeds synthetic retained rows, applies 0020 and checks retention, both namespaces, all ranking statuses, restoration, exact saved retries, rejected new publications, rollback of native update events, and real PostgreSQL lock waiters. It verifies the container identity and removes only that invocation's fixture; it never uses retained community databases. The PostgreSQL image must already be available locally. `ILLYA_AVAILABILITY_POSTGRES_IMAGE` may select the verified lowercase image ID.
